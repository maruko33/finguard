## Phase 9 finance database foundation

Finance mappings live in `finance.domain`, separate from the Phase 8 risk transaction model. V2 adds six tables; V1 and `transactions` are unchanged. The original reviewed proposal is preserved in `docs/phase9/`.

From the repository root, configure `.env` from `.env.example` without committing credentials, then run `docker compose up -d postgres`. From this service run `AWS_REGION=ca-central-1 python3 scripts/mvn-local.py clean package`. The region permits the existing Phase 8 SQS bean to initialize; tests do not send SQS messages. Flyway applies V2 automatically; Hibernate validates mappings. Back up meaningful local data before applying migrations. Do not reset volumes. The integration tests require PostgreSQL 17, migrate V1 + V2 into a randomly named isolated schema, and remove only that test schema afterward. They use `DB_URL`, `DB_USERNAME`, and `DB_PASSWORD` supplied by the helper; they do not use Testcontainers.

Two corrections to the proposed SQL: explicitly require a non-null source row when source batch is present (SQL CHECK treats UNKNOWN as passing); require candidate entry type when a category is present (MATCH SIMPLE otherwise bypasses the category owner/type FK). No other DDL changes. All proposed indexes remain.

Finance APIs remain unimplemented/unexposed: verified authentication and owner authorization are prerequisites. These are persistence foundation mappings with read-only association views and scalar FK columns; workflow constructors/mutations, repository interfaces and locking queries are deferred together with confirmation services. Import batches already carry `@Version`. No repository interfaces were added.

Remaining risks: `NUMERIC(19,2)` rounds excess input decimals in PostgreSQL, so future write paths must use `Money` (rejects rounding) and validate candidate amounts before persistence. Currency codes are syntactically checked, not an ISO currency registry or account-currency match. Batch lifecycle transitions and ledger-only-after-confirmation are service responsibilities; only terminal timestamp consistency is enforced by DDL. Duplicate acknowledgment freshness, same-account serialization, trusted bank ID policy, retention cleanup, privacy erasure, and concurrency tests belong to subsequent authenticated workflow work. No finance service logs or uploads exist; keep SQL parameter logging disabled when handling real financial data.
